# 系统配置与限流设计

版本：v1.1.0
日期：2026-09-08
状态：现行

## 1. 概述

系统配置（SystemConfigs）用于存储可热更新的运营参数。本设计文档记录 2026-08-30 重构后的完整行为，包括配置项清单、消费方、限流身份识别机制与配置写入校验。

此前系统配置存在两类问题：
- 死配置：部分配置项写入后无任何代码读取（如 User 组的 EnableRegistration 等）。
- 限流身份识别失效：限流中间件注册在认证之前，所有请求被当成游客并按出口 IP 限流，导致 RateLimit.User/Premium 配置不可达。

本次重构后：配置项精简为 13 项、分组 3 组，每项均有真实消费方；限流改为按用户身份（UserId/ClientId/角色）分配配额。

v1.1.0 补充：内部服务间调用（BFF→API）豁免用户级限流的机制，及 public 搜索端点无条件时不再返回 400 的行为修正。

## 3. 限流机制

### 3.1 身份识别

限流中间件注册在 `UseAuthentication` 与 `UserContextMiddleware` 之后、`UseAuthorization` 之前。身份识别优先级：

1. 客户端认证（sync-client 等）：读 `Items["ClientId"]`，限流键为 `client_{ClientId}`，用户类型 `merchant`。
2. 已登录用户：读 `UserId`，限流键为 `user_{UserId}`，用户类型由角色推导。
3. 会话用户：读 `SessionId`，限流键为 `session_{SessionId}`。
4. 游客：限流键为 `ip_{ClientIp}`，用户类型 `guest`。

### 3.2 用户类型推导（UserContextMiddleware）

依据 `UserDto.Roles` 推导 `Items["UserType"]`：

- 含 `Admin` / `SuperAdmin` / `MerchantAdmin` → `admin`
- `merchantId` 非空且含 `MerchantStaff` / `MerchantAdmin` → `merchant`
- 其余登录用户 → `user`
- 游客 → `guest`

### 3.3 配额映射

限流中间件按用户类型从配置读取对应 `RequestsPerMinute`，每分钟滑动窗口计数。超过限制返回 429，响应头 `Retry-After` 为需等待秒数。

### 3.4 白名单与豁免

跳过用户级限流的情形：

- 健康检查路径（/health、/healthz、/health/live、/health/ready、/readyz）。
- `/api/sync/` 前缀路径（Sync→API 机器间通信）。
- 内部服务间调用（v1.1.0 新增）：请求头 `X-Internal-Token` 等于配置 `Internal:ApiToken` 时豁免。见 3.6。

### 3.5 并发与内存

滑动窗口的"读取过期记录 + 检查 + 写入"在单条用户队列的锁内原子完成；每 5 分钟清理空闲超过 5 分钟的队列条目，防止内存无界增长；读取失败（数据库不可用）时最长缓存 30 秒再重试，避免故障期查库洪泛。

### 3.6 内部服务间调用豁免（v1.1.0）

背景问题：API 无公网 ingress，移动端 App 的所有请求经 Mobile BFF 这一个 Pod 转发到 API。BFF 调用 public 端点时不带用户令牌，API 侧一律按游客、以来源 IP（即 BFF 的单一 Pod IP）计入 `ip_*` 桶，guest 配额 30/分钟。而一次搜索页加载即产生约 6 次 API 调用（bearings/search、merchants/search、home 内部再聚合 hot/merchants/brands/bearing-types），正常浏览几个页面、叠加客户端重试，很快突破 30/分钟触发 429；429 被 BFF 的 ApiClient 吞成空结果，前端表现为"搜索无结果"，且一旦进入限流窗口会连锁放大。

解决：按 IP 的游客限流对"只有内网可达、且经单一 BFF 转发"的 API 而言是错误层级的节流。改为——

- BFF 的 "Api" HttpClient 统一附带请求头 `X-Internal-Token`，取值来自配置 `Internal:ApiToken`（BFF Program.cs）。
- API 的 RateLimitingMiddleware 注入 `IConfiguration`，读取 `Internal:ApiToken`；当请求头与之相等时直接放行、跳过用户级限流。
- 令牌值经 K8s ConfigMap 注入两侧（API `openfindbearings-api-config` 与 BFF `openfindbearings-mobile-config` 的 `Internal__ApiToken`），必须完全一致；轮换时改两处并重启两服务。
- 安全性：API 仅集群内可达（无公网 ingress），该令牌只用于豁免内网聚合流量的 IP 限流，非对外凭据；真正的边缘限流由 nginx / BFF 承担。

## 4. 配置写入校验

更新配置（`PUT /api/admin/config/{key}`）经 `UpdateSystemConfigCommandValidator` 校验：

- 布尔型（Price.ShowNegotiableLabel、Price.NumericForSorting）：限定 true/false/1/0/yes/no/y/n/on/off，与 `SystemConfigRepository.TryParseBool` 识别范围一致。
- 价格可见性（Price.DefaultVisibility）：限定 Public 或 LoginRequired。
- 价格提取正则（Price.ExtractPattern）：必须是可编译的正则表达式。
- 限流阈值：必须为 1 至 100000 的整数。
- 可信度分值：必须为 0 至 100 的整数。

校验失败时返回 400 并附带具体错误信息，配置不被写入。

## 5. 缓存与失效

### 5.1 API 端（IPriceConfigProvider，Singleton）

缓存 5 分钟。`UpdateSystemConfigCommandHandler` 不再负责失效——事务由 UnitOfWorkBehavior 在 Handler 返回之后才提交，若在 Handler 内失效，并发请求会在提交前重新加载旧值并缓存，使失效被覆盖。失效动作上移到 AdminEndpoints 的 `mediator.Send` 返回之后，仅对 Price. 前缀的配置键触发。

### 5.2 Admin 端（PriceConfigService，Singleton）

读取 `GET /api/admin/config/price`，缓存 5 分钟。读取失败时设置 1 分钟退避窗口（与 _cached 是否为 null 解耦，冷启动失败也能生效）。`Update` 成功后调用 `Invalidate()` 主动失效。

## 6. 变更日志

### v1.1.0（2026-09-08）

- 新增内部服务间调用豁免（3.6）：BFF→API 带 `X-Internal-Token`（配置 `Internal:ApiToken`），API 限流中间件识别后跳过按 IP 的用户级限流。根因是 API 无公网 ingress、全部 App 流量经单一 BFF Pod IP 转发，guest 30/分钟被聚合流量误伤导致 429→空结果。
- 修正 public 搜索端点行为：`SearchBearingsQueryHandler` 移除"至少一个搜索条件"的强校验（原抛 InvalidOperationException 被 ExceptionHandlingMiddleware 映射为 400），无条件下返回空/全量分页结果，与商家搜索此前移除同类校验保持一致。
- 配置注入：API `openfindbearings-api-config` 与 BFF `openfindbearings-mobile-config` 各加 `Internal__ApiToken`（同值）；两侧 appsettings.json 加 `Internal:ApiToken`。

### v1.0.0（2026-08-30）

- 初始版本。记录重构后的 13 项配置、3 组分组、各项消费方。
- 明确限流按用户身份而非 IP 识别，并给出档位推导规则。
- 明确配置写入校验规则与缓存失效时机。
